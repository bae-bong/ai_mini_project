# 분야별 자료 등록과 중복 점검

## 작업 순서와 완료 범위

1. 최신 develop의 법령·사업공고 적재 API와 PostgreSQL 컬렉션을 비교했다.
2. 자료 관리의 경영지원은 `/upload-paper`와 `pdf`, 사업공고는 `/upload-notice`와 `web`으로 연결했다.
3. 복수 선택·드래그앤드롭, 파일별 상태, 순차 업로드, 실패 파일 재시도를 구현했다. PDF만 허용하며 파일당 20MB, 선택 목록당 최대 20개다.
4. 신규 업로드에 해시를 기록하고 동일 컬렉션의 재등록을 건너뛴다. 같은 이름의 수정본은 기존 파일 청크를 교체한다. 공고 개요·본문은 한 트랜잭션으로 저장한다.
5. 기존 DB 중복은 조회 전용 도구로 점검한다. 운영 후보 확인·백업·삭제는 아직 수행하지 않았다.

## 분류와 기존 기능 보존

- 경영지원의 `노무 법령 / 기업 지원 근거법`은 법령 내부 분류다. 사업공고 저장 위치를 선택하는 드롭다운이 아니다.
- 사업공고에 PDF만 올리면 파일명으로 제목과 안정적인 공고 ID를 만든다. 신청기간·지원대상은 자동으로 구조화하지 않는다. 해당 정보는 본문 검색 대상이다.
- 기존 수집 도구의 `meta` JSON + 선택 첨부 PDF 계약도 유지한다. 공식 공고 ID, 기간, 기업 유형 등을 알고 있다면 이 경로를 사용한다.
- 기존 law_pipeline 관리 법령에는 수동 업로드를 섞지 않는다. 해당 컬렉션은 기존처럼 409와 담당자 안내를 유지한다.
- 문서 내용이 실제 법령인지 사업공고인지 자동 판정하지 않는다. 사용자가 선택한 탭이 저장·검색 분야를 결정한다.
- 자료는 기존과 같이 로그인 사용자 사이에 공유된다. 관리자 권한·개별 사용자 자료함은 이번 변경에 포함하지 않는다.

## 중복 기준과 한계

- 새 법령 업로드는 PDF 원본 바이트의 SHA-256으로 비교한다. PDF만 등록한 사업공고도 같은 방식이다. 같은 PDF의 파일명만 바꿔도 제외한다.
- 메타 JSON을 명시한 사업공고는 PDF와 메타를 함께 비교하므로 메타 수정은 새 적재로 처리한다.
- 파일 바이트가 다른 재출력 PDF, 법령과 공고 사이의 중복, 과거 해시가 없는 자료는 신규 해시 검사로 제거하지 않는다.
- 조회 도구는 동일 컬렉션에서 파일 전체 청크와 법령·공고 식별 정보가 같은 후보만 묶는다. 조항 한 개의 반복을 문서 중복으로 보지 않는다. 개요와 첨부도 독립적으로 비교한다.
- 원본 PDF는 DB에 보관하지 않고 텍스트·메타·벡터를 저장한다. DB의 중복 정리는 해당 문서에 속한 청크를 대상으로 한다.

## 운영 반영 후 중복 조회

먼저 새 코드를 배포하고 RAG 이미지를 다시 빌드해야 도구를 사용할 수 있다. 운영 DB는 이 작업 공간에서 직접 접속하거나 수정하지 않았다.

EC2의 저장소 루트에서 실행한다.

```bash
sudo docker compose -f compose.yaml -f compose.public.yaml \
  exec -T rag python -m tools.audit_duplicate_documents \
  > /tmp/ai-mini-duplicate-report.json
cat /tmp/ai-mini-duplicate-report.json
```

도구에는 삭제 기능이 없다. 후보가 나오면 남길 `source_file`과 제거할 `source_file`을 먼저 확인한다. `source_file`이 없는 청크는 파일 경계를 알 수 없어 자동 분류하지 않는다. 후보가 없다는 결과가 모든 원본 파일의 유일성을 증명하지는 않는다.

실제 정리 전 백업:

```bash
umask 077
sudo docker compose -f compose.yaml -f compose.public.yaml \
  exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > "$HOME/ai-mini-before-dedup-$(date +%Y%m%d-%H%M%S).sql"
```

후보별 확인과 백업 후 정확한 컬렉션·파일 키에 한정해서 삭제한다. 컬렉션 전체 초기화나 `down -v`는 사용하지 않는다. law_pipeline 관리 컬렉션의 중복은 원본 목록과 전처리부터 확인하고 재적재 방식으로 정리한다.

## 검증

프론트 로직은 `node --test frontend/tests/*.test.cjs`로 검사한다. 백엔드 API 검사는 `python -m unittest discover -s tests -v`로 수행한다. DB 테스트는 `RUN_DB_TESTS=1`과 **별도 폐기 가능한 DB**가 필요하며 운영 DB에서 실행하면 안 된다.

브라우저 확인은 로컬 화면에서 인증·업로드 응답을 테스트 대역으로 제공했다. 실제 유료 임베딩 API와 EC2 업로드는 별도 검증 대상이다.
